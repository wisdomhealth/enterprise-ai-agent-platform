# Enterprise AI Agent Platform 生产纵向切片设计

状态：已完成分节评审，等待用户对本文档进行最终审阅  
日期：2026-08-09

## 1. 背景与目标

本项目从空仓库开始，目标不是一次性实现招聘描述中的全部平台能力，而是先交付一个可生产运行、可验证、可交接的纵向切片。首版服务于单一企业组织，面向 5–25 名内部员工、最多 10,000 份知识文档和每天不超过 1,000 封新邮件。

纵向切片包含两条客户服务链路：

1. 外部客户通过公开 Web Chat 与 AI 交流。AI 可以直接回复；当客户主动要求、连续无法回答、检索置信度不足、涉及敏感主题或系统异常时转人工，并把完整上下文交给客服。
2. Gmail 收件由 AI 分类并生成有知识依据的回复草稿。草稿必须经过内部审核员批准，系统才可以通过 Gmail API 发送。

知识库首个来源是 Google Drive 中管理员明确授权的目录及允许的子目录，支持 PDF 和 Word 文档。客户侧默认使用英文回复，但语言不作为子系统硬编码限制。

首版采用 Claude 作为唯一完成生产验证的 LLM 提供商，通过轻量适配边界避免业务层直接依赖供应商。持久化使用 PostgreSQL + pgvector，后台任务使用 Celery，Redis 仅用于任务传输、短期缓存、限流和临时实时广播。部署目标是 Docker Compose + 单台云服务器。

## 2. 设计原则与总体方案

采用“模块化单体 + 独立后台任务进程”，而不是从第一天拆分微服务，也不让 n8n 承载核心业务状态。

选择该方案的原因：

- 各子系统具有明确职责、数据契约、状态机和验收结果，可以独立开发与交付。
- 首版只有一套部署、数据库和故障排查路径，适合单服务器与非技术负责人后续维护。
- PostgreSQL 是持久化事实来源，避免分布式事务和跨服务一致性成本。
- 模块通过应用服务、稳定 schema 和领域事件协作，未来出现真实团队边界或容量瓶颈时可以拆分服务。

不采用的方案：

- 首版微服务：会过早引入服务发现、分布式追踪、消息一致性和多套部署流水线。
- n8n 主导核心编排：会把聊天、审批和邮件生命周期分散到两个状态系统，削弱审计、幂等和恢复能力。

## 3. 可独立交付的子系统

每个子系统必须包含自身需要的数据模型、API、后台任务、界面、自动化测试、评测证据和基本可运维能力，不能只交付底层代码。

| 编号 | 子系统 | 职责与可验收结果 | 依赖 |
|---|---|---|---|
| S0 | 平台基础 | 单组织用户体系、管理员/审核员/普通成员角色、登录、组织级与资源级授权、配置、审计、Outbox 和任务恢复基础 | 无 |
| S1 | Google Drive 知识摄取 | 专用连接身份、授权目录白名单、PDF/Word 解析、版本化分块与嵌入、15 分钟增量同步、手动同步、删除撤权、隔离与重试 | S0 |
| S2 | 可信 RAG 核心 | pgvector 与 PostgreSQL 全文检索并行召回、候选阶段权限过滤、RRF 融合、引用、拒答、纵深防御、Claude 适配、Staff Assist 和离线评测 | S1 |
| S3 | 外部客户 Web Chat | 公开聊天页面、匿名会话、可选姓名/邮箱、校验后流式响应、安全引用、分层限流和保留策略 | S2 |
| S4 | 人工客服接管 | 混合转人工规则、工作台、原子认领、人工实时回复、AI 暂停/恢复、完整上下文移交和离线队列 | S3 |
| S5 | Gmail 邮件分流 | Gmail 增量收件、邮件分类、知识检索、版本化草稿生成、重复事件幂等和可恢复任务 | S2 |
| S6 | 审核与邮件发送 | 审核队列、编辑/重新生成/批准/拒绝、批准失效规则、Gmail 发送、防重复发送、结果核对与完整审计 | S5 |
| S7 | 管理与运营 | 连接器、授权目录、文档与同步状态、用户权限、失败任务、保留期与删除、质量和成本指标 | S0–S6 |
| S8 | 生产运行基线 | 持续建设的健康检查、日志、指标、告警、密钥、备份、PITR/WAL、恢复演练、部署与运维手册；M6 完成最终加固 | 贯穿所有里程碑 |
| S9 | n8n 外围自动化 | 后续订阅版本化领域事件和 Webhook，连接 Slack、CRM、Google Sheets 等；不承载核心聊天或邮件状态 | S0，后续版本 |

推荐依赖顺序是 S0 → S1 → S2；之后 S3–S4 与 S5–S6 可以部分并行；S7 随各业务模块演进；S8 从首个里程碑开始持续交付；S9 位于首版之后。

## 4. 运行时架构与模块边界

### 4.1 Next.js Web 应用

同一 Web 应用提供：

- 外部客户公开聊天页面。
- 客服工作台。
- 邮件审核队列。
- 管理与运营后台。

不同页面使用独立路由、身份和权限边界。首版不拆成多个前端项目，也不提供跨站嵌入式聊天组件。

### 4.2 FastAPI 模块化后端

后端按照身份权限、知识摄取、检索生成、客户聊天、人工客服、邮件分流、审批发送、运营管理和外部集成划分模块。

模块不得直接绕过其他模块的应用服务操作其内部状态。跨模块同步操作使用应用服务和严格 schema；异步副作用通过事务 Outbox 发布领域事件。

### 4.3 Celery 后台任务

后台任务负责：

- Google Drive 和 Gmail 增量同步。
- 文档解析、分块、嵌入和版本发布。
- 邮件分类、检索和回复草稿生成。
- 已批准邮件的发送、核对和安全重试。
- 保留期清理、删除账本执行和周期性一致性检查。

PostgreSQL 保存完整且可恢复的任务意图，包括业务参数引用、状态、尝试次数、租约、下次执行时间和结果。Celery 消息只表示需要尝试执行工作，不是业务事实来源。

数据库租约或锁防止同一任务被并发执行。任务必须允许重复投递，并通过幂等键和状态条件更新安全恢复 Worker 崩溃、租约过期和重复执行。

### 4.4 PostgreSQL、pgvector 与 Redis

PostgreSQL 保存用户、权限、连接器、文档版本、分块、向量、会话、消息、邮件生命周期、草稿版本、审批、发送意图、任务、审计、Outbox 和删除账本。

Redis 用于 Celery 传输、短期缓存、限流计数和在线 SSE 事件扇出。Redis 实时消息是临时广播；Redis 丢失或重启后，客户端和 Worker 必须从 PostgreSQL 恢复权威状态。

### 4.5 Outbox 语义

业务状态与 Outbox 事件在同一 PostgreSQL 事务内提交。分发器提供至少一次投递，不提供恰好一次保证。消费者使用 event_id 或业务幂等键记录处理结果，并必须安全处理重复事件。

分发器故障恢复后扫描未发布事件继续投递。达到重试上限的事件或任务进入 PostgreSQL 持久化失败队列，由管理员在修复原因后按原状态机重新执行。

## 5. 身份、授权与核心数据边界

首版是单组织产品，但 organization_id 只是隔离维度之一，不等同于完整权限控制。每次读取和写入都必须同时执行：

- 组织级授权。
- 用户角色与操作权限。
- 资源级授权，包括知识库、会话、邮件和管理资源。
- 当前资源状态约束。

员工账户采用邀请制，包含：

- 管理员：用户、连接器、授权目录、配置、数据删除和运营管理。
- 审核员：邮件审核、发送、客户会话认领和人工回复。
- 普通成员：仅访问被明确授权的内部运营与 Staff Assist 能力。

员工登录身份与 Google Drive/Gmail API 连接凭证分离，登录令牌不能直接访问连接器。

外部客户只通过公开聊天页面访问。匿名客户获得短期、不可枚举的会话凭证，该凭证只授权访问对应会话。系统对 IP、会话和组织执行分层限流。

## 6. Google Drive 摄取与可信检索

### 6.1 Drive 安全范围

Customer Chat 的知识只来自管理员配置的 Google Drive 知识库目录及明确允许的子目录。

生产环境优先使用专用连接身份，只向该身份授予知识目录的只读权限。Drive API 凭证只申请读取知识所需的最小 scope，不得具有修改或删除 Drive 内容的权限。

应用层在摄取和召回时再次按授权 folder ID、organization_id、资源权限和文档可检索状态强制过滤。授权目录外的文件不得被摄取、索引或召回。

### 6.2 文档生命周期

Drive 变更依次经过：

发现变更 → 获取文件 → 解析 → 分块 → 嵌入 → 发布可检索版本

每次文件变化产生独立文档版本。新版本完整处理成功后，才原子切换为当前可检索版本；失败不会破坏上一可用版本。

一旦同步检测到文件被删除、移出授权范围或连接身份失去读取授权，立即将相关版本标记为不可检索。物理分块、向量和派生数据由后台任务异步清理。只有一批变更可靠写入 PostgreSQL 后，才推进同步游标；单个失败文件进入隔离状态，不阻塞其他文件。

### 6.3 Hybrid 检索

首版候选召回同时执行：

- pgvector 向量相似度检索。
- PostgreSQL 全文检索。

两个分支必须在候选生成阶段分别强制执行组织级、资源级、授权目录、文档状态和其他元数据过滤，不能先召回越权候选再在融合后删除。

候选使用 RRF 等与具体评分尺度无关的方式融合。重排序器作为可插拔阶段，只有在固定评测集上稳定改善关键指标，且延迟和成本可以接受时，才在首版启用。

查询流程是：

问题规范化 → 双路权限过滤候选召回 → RRF 融合 → 可选重排序 → 上下文安全检查 → Claude 生成 → 引用映射与 groundedness 基本校验 → 输出

没有足够依据或引用不能验证时，系统明确回答不知道，并可以按策略触发转人工。

## 7. 客户聊天与人工客服状态机

客户聊天状态机是：

AI_ACTIVE → HANDOFF_REQUESTED → QUEUED → HUMAN_ACTIVE

从 HUMAN_ACTIVE 只能发生以下转换：

- HUMAN_ACTIVE → RESOLVED
- HUMAN_ACTIVE → AI_ACTIVE，由客服明确执行 Resume AI

系统不得因为超时、页面刷新、客服离线或重启自动恢复 AI。Resume AI 后不发送人工接管期间产生或遗留的旧 AI 回复；系统等待客户下一条消息或新的明确触发后才生成新回复。

转人工时持久化完整消息记录、会话摘要、引用来源、客户资料、转人工原因和相关工具结果。客服认领使用数据库原子条件更新或乐观版本控制，避免双重认领；冲突返回 409 Conflict、当前状态和当前版本。

客户模型输出不会把 Claude 原始 token 直接转发。系统先完成整条答案的引用映射与 groundedness 基本校验，再按句段通过 SSE 渐进输出。客户只看到安全处理后的文档标题、章节、页码等引用，不得看到内部路径、folder ID、chunk ID 或私有 Drive 链接。

内部客服可以在工作台使用 Staff Assist 查询知识库，查看更完整的 chunk、文档版本和内部 Drive 链接。Staff Assist 结果只供员工参考，不能自动产生客户侧副作用。

## 8. 邮件生命周期、审核与 Gmail 发送

### 8.1 生命周期

主状态流：

INGESTED → DRAFTING → AWAITING_REVIEW → APPROVED → SEND_PENDING → SENDING → SENT

补充状态与转换：

- DRAFTING → DRAFT_RETRY_WAIT → DRAFTING。
- AWAITING_REVIEW → DRAFTING → AWAITING_REVIEW，用于带审核指令的重新生成。
- AWAITING_REVIEW → REJECTED。
- SENDING → SEND_RETRY_WAIT → SEND_PENDING，仅适用于明确知道未发送的错误。
- SENDING → DELIVERY_UNKNOWN，用于 Gmail 可能已发送但本地未获得明确响应。
- 不可恢复错误或超过上限后进入 FAILED_TERMINAL。

每次转换记录操作者、原因、前后状态、资源版本、关联 ID 和时间。人工重试必须走相同状态机、授权、幂等和外部核对规则，不能直接修改状态或绕过约束。

### 8.2 草稿版本与批准失效

每个草稿版本保存：

- 草稿正文、收件人和 Gmail 线程关键字段。
- 审核指令。
- 模型、提示词和检索配置版本。
- 引用与来源版本。
- 创建者及创建时间。

任何已批准草稿的正文、收件人或线程关键字段发生修改时，原批准立即失效，状态必须返回 AWAITING_REVIEW 并重新审核。

邮件审核页提供只读 Staff Assist，复用 S2 RAG Core。其结果不能直接覆盖草稿或触发发送，必须经过明确编辑和审批动作。

### 8.3 防重复发送与不确定结果恢复

Gmail 原始邮件 ID 唯一约束防止重复摄取。每次批准产生唯一 delivery_intent_id；数据库约束保证同一 delivery_intent_id 最多记录一个成功发送结果。

发送前锁定发送意图，生成确定性 MIME Message-ID，并持久化发送尝试。成功后保存 Gmail 消息 ID 和线程 ID。

明确未发送的临时错误可以指数退避重试。若发生“Gmail 已在外部发送，但本地响应超时”等不确定情况，进入 DELIVERY_UNKNOWN。核对流程按确定性 Message-ID、线程和收件信息检查 Gmail 已发送邮件；核对完成前禁止任何再次发送。

数据库约束、确定性 Message-ID 和发送后核对只能尽最大可能避免外部重复发送，不能把第三方系统副作用表述为绝对恰好一次。

## 9. OAuth 与秘密管理

OAuth 刷新令牌使用信封加密：

- 每个凭证使用独立数据密钥加密。
- PostgreSQL 只保存密文、被主密钥加密的数据密钥和密钥版本。
- 生产主密钥必须由 KMS、Secret Manager 或等效独立密钥设施提供，不得存入 PostgreSQL、镜像或源代码。
- 本地主机密钥只允许用于开发环境或客户明确选择的自托管部署。
- 设计支持主密钥轮换、凭证撤销和 REAUTH_REQUIRED 状态。

## 10. 安全与数据治理

### 10.1 Prompt Injection 纵深防御

Google Drive 文档、聊天消息和邮件正文都视为不可信输入。系统采用纵深防御降低 Prompt Injection 风险，不宣称能够绝对阻止攻击：

- 强制权限过滤和来源白名单。
- 系统指令与检索内容明确隔离。
- 检索内容不能获得系统指令或工具权限。
- 工具采用固定白名单、严格 Pydantic schema 和服务端授权。
- Customer Chat 不开放产生外部副作用的工具。
- Gmail 发送只能来自已批准的 delivery intent。
- 对异常输入、输出和工具请求进行检测、限制、审计和安全失败。

### 10.2 日志与模型数据最小化

日志默认不记录 OAuth 令牌、完整邮件正文、完整聊天正文或完整模型提示，只记录关联 ID、状态、耗时、错误类别和脱敏摘要。

发送给 Claude 的内容限制为任务所需的最小上下文。上线前必须确认实际 API 账户的数据使用和保留配置符合业务要求，不能假设供应商默认不保留数据。

### 10.3 保留与删除

产品默认值为聊天和邮件内容保留 90 天、审计事件保留 1 年，但均可配置。这些默认值不是已经满足法律或行业合规要求的保证；最终期限必须由客户根据业务和法律意见确定。

删除覆盖会话、邮件内容、文档版本、分块、向量和派生摘要。系统维护持久化且数据最小化的 erasure ledger，记录删除请求标识、范围、执行状态和必要校验信息，不保留被删除正文。

旧备份通过生命周期过期，不做原地修改。从旧备份恢复后，必须先重放 erasure ledger，使历史删除再次生效，再恢复正常服务。

## 11. 产品界面与接口

### 11.1 客户公开聊天页面

客户可以匿名开始会话、可选提供姓名和邮箱、接收校验后的渐进回复和安全引用、主动请求人工、查看 AI/排队/人工状态，并在客服离线时留下联系方式。

首版不提供客户注册、客户历史会话门户、附件上传、语音或嵌入式聊天组件。

### 11.2 客服工作台

工作台提供待接管、处理中和已解决队列，展示完整会话、AI 回复、内部来源详情、转人工原因和客户资料。客服可以原子认领、实时人工回复、写内部备注、解决会话或明确 Resume AI。

### 11.3 邮件审核队列

审核员可以按状态、分类、时间和失败类型筛选，查看原邮件、草稿、引用、分类依据、草稿版本和状态历史，执行编辑、重新生成、批准、拒绝和受控恢复。

SEND_RETRY_WAIT 与 DELIVERY_UNKNOWN 必须清晰区分；后者只提供发送结果核对，不提供直接重发。

### 11.4 管理与运营后台

管理员可以管理用户角色、Google 连接身份、知识目录、文档版本、同步游标、失败文件、保留期、删除请求、失败任务、队列积压、质量指标、成本和连接器重新授权。

### 11.5 API、SSE 与 Webhook

- API 使用明确版本，例如 /api/v1。
- 公共聊天 API 与员工 API 使用不同认证和限流策略。
- 公共客户端不能直接调用检索或模型接口。
- SSE 只发送已经完成引用与基础 groundedness 校验的答案句段和状态事件。
- 断线重连按 PostgreSQL 消息序号恢复。
- 写操作幂等键绑定组织或会话、操作者、操作类型和业务对象。
- 并发状态变化采用数据库原子更新或版本控制，冲突返回 409 和当前版本。
- 请求与响应使用严格 schema。

后续 n8n Webhook 来自持久化 Outbox，支持至少一次安全重投。消费者按 event_id 幂等。Webhook 投递包含 event_id、event_type、event_version、occurred_at 和 delivery_attempt，并通过签名、时间戳及合理有效窗口区分安全重投与恶意 replay attack。签名和时间戳可以位于经过规范化定义的 HTTP 头中，但属于完整 Webhook 安全契约的一部分。

## 12. 错误处理与恢复

错误分为：

- 可重试：超时、限流、临时网络或供应商故障，使用带抖动指数退避并遵守 Retry-After。
- 不可重试：授权不足、不支持文件、无效配置或业务校验失败，停止自动重试并要求人工处理。
- 结果不确定：外部操作可能完成，禁止重复副作用，先核对。
- 安全错误：越权、令牌异常、签名失败或可疑输入，拒绝、脱敏记录并按阈值告警。

连接器语义：

- Drive/Gmail 只有在一批数据可靠写入 PostgreSQL 后才推进同步游标。
- 一旦检测到 Drive 授权丢失，受影响内容立即不可检索。
- 凭证撤销进入 REAUTH_REQUIRED。
- Claude Chat 故障时不伪造答案，显示通用提示并提供或触发转人工。
- Claude 邮件草稿故障保留原邮件和可恢复意图。
- 连续供应商故障触发短期熔断；首版不自动切换未经验证的模型。

每个子系统必须提供 live、ready 和依赖降级状态、结构化日志、关联 ID、成功/失败/重试/耗时指标、积压与最后成功时间、管理员可见失败记录、安全恢复入口和最小故障处理说明。

## 13. 生产运行基线

S8 从 M0 开始持续实施，不是 M6 才开始。M6 负责统一检查、故障演练和最终加固。

生产基线包括：

- TLS、反向代理、安全响应头和请求限制。
- KMS/Secret Manager、凭证轮换和最小权限。
- 结构化日志、指标、仪表板与告警。
- 数据库、同步陈旧、任务积压、模型错误、人工队列和 Gmail 不确定发送监控。
- PostgreSQL 加密备份、PITR/WAL 或等效连续备份。
- Redis 不作为恢复来源。
- 定期恢复演练和 erasure ledger 重放。

目标 RPO 不超过 15 分钟、RTO 不超过 4 小时。它们是必须通过实际演练验证和记录的运营目标，不是未经验证的 SLA 保证。若演练未达到目标，必须记录风险和改进措施。

## 14. 测试、AI 评测与发布门槛

### 14.1 测试层次

- 单元测试：状态机、权限、分块、RRF、引用、重试、租约和保留期。
- 真实数据库集成测试：PostgreSQL + pgvector 事务、约束、Outbox、并发认领、双路检索和权限过滤。
- 外部契约测试：固定 Drive、Gmail 和 Claude 响应，覆盖分页、限流、令牌失效和异常响应。
- 端到端测试：文档到回答、邮件到审核发送、AI 对话到人工接管。
- 故障与恢复测试：重复任务、Worker 中断、租约过期、Redis 清空、超时、不确定外部结果、PITR 和删除账本重放。

CI 不依赖真实客户账号；真实 Google 和 Claude 验证在受控预发布环境执行。

### 14.2 评测数据

评测集分为：

- 固定回归集：开发过程中持续运行，可以用于定位退化。
- 保留验收集：不用于日常调参，只在里程碑和发布验收时运行。

数据覆盖可回答、应拒答、多文档组合、相似错误干扰、Prompt Injection、已删除、越权和授权范围外文档。

每次评测记录数据集、文档、分块、嵌入模型、检索、RRF、可选 Reranker、提示词和 Claude 模型版本。

### 14.3 硬性发布门槛

以下任一失败都阻止发布：

- 组织级或资源级越权。
- 任一检索分支召回授权范围外内容。
- 客户引用不能映射到本次实际召回片段。
- 客服接管后 AI 仍发送消息，或超时自动 Resume AI。
- 未批准或批准已失效的邮件产生发送意图。
- DELIVERY_UNKNOWN 核对完成前再次发送。
- 人工重试绕过状态机、幂等或核对。
- Gmail 外部已发送但本地超时的故障注入产生再次发送。
- 日志、错误或审计泄露令牌和完整敏感正文。
- PITR、Redis 丢失恢复或 erasure ledger 重放无法完成。

### 14.4 模型质量目标

首版初始目标：

- 权威文档 Recall@10 ≥ 0.85。
- 人工抽检引用支持率 ≥ 95%。
- 不可回答问题正确拒答率 ≥ 90%。
- 邮件分类宏平均 F1 ≥ 0.85。
- Pydantic 结构化输出解析成功率 ≥ 99%。

同时评测：

- 答案级 groundedness。
- 事实主张级 groundedness：拆分可核验主张并检查是否由引用内容支持。
- 检索延迟、模型延迟、端到端延迟。
- 每次请求的 token 和模型成本。

这些是模型质量和产品改进目标，不与安全硬门槛混同，也不是永久 SLA。Hybrid 与 Reranker 只有在质量收益相对于延迟和成本基线明确时才保留或启用。

## 15. 交付准备门、里程碑与变更控制

### 15.1 正式准备门

10 周目标排期只有在以下条件全部满足后才开始：

- 客户确认首版范围、角色和验收负责人。
- Google Cloud 项目、Drive/Gmail API 和专用连接身份可用。
- 获准知识目录、代表性 PDF/Word 和脱敏邮件样本可用。
- Claude API 账户及数据使用配置确认。
- 回归集与保留验收集的构建责任人、初始样本和标注规则确认。
- 生产服务器、域名、TLS、KMS/Secret Manager 和备份存储方案确认。
- 客服升级规则、在线时间、邮件分类和人工审批规则确认。

准备门未通过时可以做风险较低的设计验证，但不开始承诺的 10 周交付时钟。

### 15.3 Scope Freeze 与变更控制

准备门通过时冻结首版范围、接口和硬性发布门槛。之后的新功能或行为变化必须：

1. 记录变更目的和验收条件。
2. 评估对子系统、状态机、数据迁移、安全、测试、工期和成本的影响。
3. 由客户产品负责人和技术负责人共同批准。
4. 明确选择调整时间、替换等量范围或进入后续版本。

缺陷修复、安全修复和已批准范围内的必要可靠性工作不被当作可删减的新范围。

### 15.4 排期压力下的 Cut Line

不得删减或绕过：

- 身份、组织级和资源级权限。
- 授权目录和双分支检索权限过滤。
- 客户输出引用/groundedness 基本校验。
- 邮件审批、批准失效、防重复和 DELIVERY_UNKNOWN 核对。
- 状态机、幂等、Outbox、数据库任务意图和恢复。
- 密钥、日志脱敏、备份恢复、删除账本。
- 硬性发布门槛与生产恢复证据。

若排期承压，按顺序优先延后：

1. 非关键管理界面美化和高级筛选。
2. Reranker。
3. 非必要分析报表。
4. Staff Assist 的高级交互，但保留基础检索能力。
5. 其他不影响安全闭环的便利功能。

不能通过降低安全或可靠性门槛来维持日期；如果 Cut Line 后仍无法按期完成，应调整发布日期。

### 15.5 每个里程碑的完成证据

每个里程碑都必须提供：

- 可运行部署或可重复运行的演示环境。
- 自动化测试结果。
- 适用的 AI 回归与验收评测结果。
- 数据迁移和接口/schema 文档。
- 健康、日志、指标和失败恢复证据。
- 运维说明、已知限制和未关闭风险。
- 对照验收条件的签收记录。

只有代码合并而没有可运行证据，不算完成。

## 16. 首版明确不包含

- WhatsApp Business API。
- HubSpot、Calendly/Google Calendar、Slack、Airtable 和 Google Sheets。
- n8n 工作流实现；首版只交付事件和 Webhook 契约。
- 多组织 SaaS、自助注册、计费和客户账户门户。
- 附件上传、语音、STT/TTS、MCP 和自托管模型。
- OpenAI 完整生产路径和自动模型故障切换。
- 微服务、Kubernetes 和自动水平扩缩。
- 未通过评测收益门槛的 Reranker。
- HIPAA、GDPR 等法律认证。系统提供治理能力，但合规结论需要客户业务与法律评估。

## 17. 子系统完成定义与最终交接

子系统只有同时满足以下条件才算完成：

- 功能和状态机实现完整。
- 组织级、资源级权限和审计有效。
- 迁移、API/schema、后台任务和必要界面已交付。
- 自动化测试、适用 AI 评测和硬性门槛通过。
- 健康、日志、指标、失败查看和安全恢复可用。
- 接口、运营、恢复说明和已知限制完整。
- 在可运行环境中演示并由负责人验收。

最终交接必须把生产控制权转移给客户，包括：

- 源代码仓库、提交历史和发布标签。
- 容器配置、部署脚本、域名、DNS 和 TLS 管理权。
- 云服务器、PostgreSQL、备份存储、KMS/Secret Manager 和监控告警所有权。
- Google Cloud 项目、Drive/Gmail 连接身份、OAuth 配置和凭证轮换责任。
- Claude API 账户、预算和用量告警控制权。
- 数据迁移记录、API 文档、状态机、架构与安全说明。
- 测试、回归集、保留验收集、评测结果和成本/延迟基线。
- PITR、RPO/RTO、Redis 恢复、Gmail 不确定发送和 erasure ledger 重放证据。
- 运营手册、事件响应步骤、已知风险和管理员培训。

交接前应完成凭证轮换，移除开发人员不再需要的生产访问，并由客户指定负责人确认生产资产和恢复能力已经接收。
